## Session A / Session B retained lock scenarios

1. **Live preparation:** A locks the shared preparing batch with `SELECT ... FOR UPDATE` and performs a valid heartbeat. B, under actual `SET LOCAL ROLE service_role`, calls `SELECT public.maintain_accession_import_once()`. It skips the locked row and may process another eligible row; it never changes A's lease/state. After A rolls back or commits the heartbeat, B re-reads the actual generation/expiry. Capture both transactions' batch state, safe audit and private-capability count.
2. **Stale generation and expired lease:** capture the shared batch token/generation. After an authorized expired-lease seed, B performs maintenance; A invokes `heartbeat_accession_preview` and `finish_accession_preview` with the original pair. Both must reject; terminal state and original generation remain intact. A mismatched token/generation must also reject before recovery. No lease reset or replay is permitted.
3. **Accepted confirmation crosses deadline:** use the retained atomic-confirmation concurrency harness to pause A only after it owns the batch lock and passes DB-clock admission. B calls maintenance at/after the original deadline and status in a separate transaction. Maintenance skips A; status reports processing. Release A to commit after deadline: status returns the durable receipt; subsequent maintenance purges only bindings. Repeat with A rollback: only then may B mark ready as expired and purge. Do not infer admission merely from HTTP timing or a held arbitrary lock.
4. **Expiry while waiting for locks:** A holds a valid preview batch lock. B starts real confirmation before its deadline and waits under the explicitly measured test lock budget. Release A after the deadline. B must reject new admission under its acquired lock; maintenance and status must agree with the committed terminal state. Reuse `accession-confirmation-atomic-concurrency.md`; do not alter sealed timestamps to simulate time passing.
5. **Status/confirm/purge race:** A owns batch lock for maintenance before DELETE; B status must return processing and B confirm must not write. Reverse ownership: A atomic-confirm lock makes B maintenance skip. After release, repeat maintenance until all eligible bindings are absent. Verify one receipt/dedup claim, unchanged mappings/business rows and no terminal reset. Other eligible rows must progress while the oldest row is locked.
6. **Outage and restart:** stop only an explicitly authorized disposable client/connection during the maintenance RPC, including before/after commit response loss. No success may be claimed on a lost response. A new one-shot invocation reconciles current DB state; it never calls confirmation. Repeated invocations cover every overdue eligible row, including deadlines missed during outage, and return idle once complete. Capture per-batch audit counts to prove no duplicate lifecycle or cleanup audit.
7. **Audit failure atomicity:** in the disposable rollback-only transaction, add a temporary failure trigger on audit insertion scoped to the synthetic maintenance event. Force an error during lifecycle/cleanup audit. Verify state, bindings and capability insertion all roll back together. Remove the temporary test trigger before the next case; never disable or replace original guard/audit triggers.
8. **Privacy after purge:** with a matched confidential client, current owner without confidential access is denied while bindings remain. After authorized terminal cleanup, that owner gets only `{state,batchId}` without original reason/count/entity data. Succeeded mappings continue to enforce current confidentiality even after bindings are gone. Wrong owner, manager and withdrawn analyst role remain denied. Capture only safe outcome/counts, no raw references or PII.
